# Git workflow

## Branches

- `main`: stable baseline; release-ready changes only after explicit owner approval.
- `develop`: integration branch; merge reviewed feature pull requests here.
- `feature/m0-foundation`: M0 implementation. No M1 work until the owner approves M0.

The initial repository has a policy-only baseline on main/develop; M0 is on the feature branch until its PR is approved and merged. The owner supplied `https://github.com/hphuc032/Fashion-AI`; it is configured locally as `origin`. A read-only `git ls-remote` check returned no heads or tags on 2026-11-05. All branches and commits created by this setup are local. Nothing has been pushed or published.

## Commits and review

Use small Conventional Commits: `chore`, `feat`, `fix`, `test`, `docs`, optionally with a scope. Inspect `git diff --cached --stat` and `git diff --cached` before every commit. Stage explicit paths; do not use forced staging to bypass ignore rules.

Never commit actual `.env` files, credentials, source videos, user projects, SQLite files/sidecars, model weights, portable runtimes, logs or generated exports. `.env.example` contains placeholders only. Synthetic fixtures are generated by script instead of committed. Ignore rules reduce accidental staging; reviewers must still inspect every newly tracked file for secrets and personal data. No tracked file-size enforcement hook is installed; inspect staged file sizes before commits.

Before PR: run the complete M0 suite with Python 3.11 and real FFmpeg/FFprobe configured. A skipped integration test does not satisfy full M0 verification. Record actual results and known limits. Review `git diff develop...feature/m0-foundation` and ensure only M0 changes are present.

## Integrating M0 (owner-approved next action)

Prepared PR body: `docs/PR_M0_FOUNDATION.md`. Base `develop`, head `feature/m0-foundation`. Do not open a remote PR or push branches without explicit approval.

After the owner explicitly authorizes publishing branches, recheck origin for new history. If it is still empty, push `develop` and `feature/m0-foundation` explicitly, then open a PR using the prepared body. If new remote history exists, fetch and reconcile it first; never force-push over it. Do not push `main` as an incidental step.

The following commands are prepared for a future approved publish, not executed during setup:

```powershell
git ls-remote --heads origin
# Only after verifying no conflicting remote history and receiving approval:
git push -u origin develop
git push -u origin feature/m0-foundation
gh pr create --repo hphuc032/Fashion-AI --base develop --head feature/m0-foundation --title "feat(m0): add local video import foundation" --body-file docs/PR_M0_FOUNDATION.md
```

After review and explicit merge approval, local merge instructions are:

```powershell
git switch develop
git merge --no-ff feature/m0-foundation -m "feat(m0): integrate verified foundation"
```

These commands are instructions only; setup does not execute them. With a hosted PR, merge into develop through the approved PR instead, then synchronize the local branch. Preserve the feature commits for review; avoid a squash unless the owner prefers it. Re-run tests on the integration result. Do not merge develop into main without separate explicit approval.

## Release gate

When M0 is verified **and the owner approves it**, propose annotated tag `v0.1.0` on the approved stable main commit after an approved develop→main integration. Do not create the tag yet. Tagging, pushing tags and publishing a GitHub release are separate actions requiring explicit authorization. Never tag an unmerged feature commit as a stable release.
